# Fitora Product Specification

## 1. Product statement

**Fitora is an AI shopping and styling agent that builds a coordinated outfit around a user's occasion, style, sizes, colour preferences, and budget, then completes the explicitly approved sandbox purchase through Prava.**

Tagline: **Style that fits the moment.**

## 2. Target user

Students and young professionals who need a gender-neutral smart-casual outfit for a specific event and want to avoid browsing and coordinating separate products manually.

Primary occasions:

- internship or job interview;
- university or workplace presentation;
- casual social event.

## 3. Problem

Conventional shopping flows make users search item by item, manually coordinate colours and styles, verify sizes and stock, keep a running total, and then repeat checkout steps. Recommendation chatbots often stop at generic advice or links. Fitora must complete a controlled journey from intent to an approved transaction.

## 4. Core user journey

1. User opens Fitora and sees a short product explanation.
2. User provides:
   - occasion;
   - total budget;
   - top size;
   - bottom size;
   - EU shoe size;
   - preferred colours;
   - optional excluded colours;
   - preferred style.
3. Fitora validates the request and generates three complete outfits from the local catalogue.
4. Each outfit shows:
   - top, bottom, and shoes;
   - requested sizes;
   - item prices and total;
   - score and concise explanation;
   - stock status;
   - remaining budget.
5. User may select an outfit or ask the agent to revise it using a constrained request, such as:
   - replace shoes with a cheaper option;
   - make the outfit more relaxed;
   - avoid white;
   - reduce the budget;
   - use more navy.
6. Fitora interprets the request, invokes deterministic tools, and displays the updated verified outfit.
7. User clicks a clear purchase action.
8. Fitora displays a final review with exact products, sizes, merchant, currency, and amount.
9. User enters an email and explicitly approves continuation to Prava.
10. Fitora creates a Prava Hosted Checkout session and redirects the user.
11. After Prava returns the user, Fitora completes the demo merchant step, reports the outcome to Prava, and shows a sanitized order result.

## 5. Functional requirements

### FR-1 Preference intake

The form must collect and validate all required fields. Budget must be represented as integer cents internally. Invalid or unsupported values must produce precise English error messages.

### FR-2 Product catalogue

The repository must contain exactly 30 fictional, logo-free products:

- 10 tops;
- 10 bottoms;
- 10 shoes.

Each product must have a stable ID, name, category, description, price, currency, merchant ID, image path, colours, available sizes, per-size stock, occasion tags, style tags, and active flag.

### FR-3 Hard filtering

A product is eligible only when:

- active;
- requested size exists;
- stock for the size is greater than zero;
- category is required;
- merchant matches the configured demo merchant.

A complete outfit is eligible only when:

- it contains one top, one bottom, and one pair of shoes;
- all sizes are available;
- total is at or below the user's budget;
- no excluded colour is present.

### FR-4 Outfit ranking

The engine must deterministically score eligible combinations using verified catalogue data. The score must include:

- occasion match;
- style match;
- colour compatibility;
- preferred-colour match;
- budget efficiency.

Return up to three distinct top-ranked outfits. Avoid returning identical combinations and avoid excessive reuse of the same products where alternatives exist.

### FR-5 Explainability

Every outfit must show a concise, factually grounded explanation. Explanations may be generated by an AI provider, but a deterministic template must be available. Explanations may reference only verified fields and computed values.

### FR-6 Agent revisions

The agent layer must support at least these intent types:

- generate outfits;
- replace top;
- replace bottom;
- replace shoes;
- make cheaper;
- change style;
- change budget;
- prefer colour;
- exclude colour;
- select outfit;
- request checkout;
- help / unsupported request.

The model output must be parsed into a strict schema before any tool runs.

### FR-7 Purchase review

Before payment, Fitora must re-read product IDs from the server catalogue and revalidate size, stock, merchant, and total. Client-supplied prices or names must never be trusted.

### FR-8 Explicit approval

Fitora must not create a real Prava session until the user has selected an outfit, reviewed the final summary, supplied the required email, and clicked the explicit payment action.

### FR-9 Prava Hosted Checkout

In real payment mode Fitora must:

- create a sandbox session on the server;
- use Hosted Checkout / full checkout;
- pass a Fitora callback URL;
- redirect to the returned hosted URL;
- recover the session securely on callback;
- poll the payment result;
- keep one-time credentials entirely server-side;
- invoke the demo merchant adapter;
- report `APPROVED` or `DECLINED`;
- display the final sanitized status.

### FR-10 Mock checkout

The same user journey must work without credentials through a mock payment adapter. Mock mode must be obvious in the UI, result screen, README, and test evidence.

### FR-11 Local persistence

Without an account system, browser storage may retain:

- last preferences;
- selected outfit;
- sanitized recent order summaries.

Do not store secrets, payment credentials, card details, or Prava session tokens in browser storage.

### FR-12 Mode visibility

A small development/status indicator must identify the active AI and payment providers. Mock or rules mode may not be hidden in screenshots intended to prove real integration.

## 6. Non-functional requirements

### Reliability

- All primary paths must handle loading, empty, error, pending, success, and declined states.
- A failed AI call must not prevent deterministic outfit generation.
- A failed payment call must not falsely show success.

### Security

- Server-only secrets.
- Zod validation.
- HMAC-signed checkout state.
- HTTP-only short-lived cookies.
- Sensitive-data redaction.
- Server-authoritative totals.

### Accessibility

- Keyboard-operable controls.
- Visible focus states.
- Form labels and helpful errors.
- Meaningful alt text.
- Sufficient contrast.
- Reduced-motion respect.

### Responsiveness

The full core journey must be usable at approximately 375 px mobile width and standard desktop widths.

### Performance

- Use optimized local images.
- Avoid loading all original high-resolution assets at full size.
- Avoid unnecessary client-side dependencies.

### Truthfulness

Documentation and UI must distinguish:

- rules fallback versus genuine model execution;
- mock payment versus Prava sandbox;
- demo merchant versus a real external retailer;
- simulated inventory versus live stock.

## 7. Out of scope

- real Amazon, Shopee, Zalora, Shopify, or brand integrations;
- scraping;
- multiple merchants in one checkout;
- live inventory synchronization;
- returns, refunds, shipping, tax, or fulfilment;
- user authentication;
- social feed or creator links;
- virtual try-on or body-image analysis;
- fashion model training;
- recommendation embeddings or vector database;
- multi-agent orchestration;
- native mobile application;
- production card processing.

## 8. Acceptance criteria

### Product

- [ ] User can complete preference form.
- [ ] Three valid outfits are generated for the standard demo input.
- [ ] Every outfit is within budget and has available requested sizes.
- [ ] User can replace at least one item through the agent interface.
- [ ] Total and explanation update correctly after replacement.
- [ ] User can review and explicitly approve checkout.

### AI

- [ ] Gemini mode can parse at least the supported revision commands when a key is configured.
- [ ] Rules mode passes the same critical commands without a key.
- [ ] Unsupported input produces a safe clarification instead of fabricated action.
- [ ] Model output cannot bypass validation or payment approval.

### Payment

- [ ] Mock flow completes end to end and is labelled mock.
- [ ] Real Prava session can be created after keys are configured.
- [ ] Hosted redirect and callback work on the deployed domain.
- [ ] Payment result is polled and handled.
- [ ] One-time credentials never appear in client responses or logs.
- [ ] Merchant result is reported to Prava.
- [ ] Final completed or failed state is shown.

### Engineering

- [ ] Lint passes.
- [ ] Type-check passes.
- [ ] Unit tests pass.
- [ ] Production build passes.
- [ ] Core Playwright journey passes in mock mode.
- [ ] Real Prava manual test evidence is recorded or blocker is explicit.
- [ ] README is accurate.
- [ ] No committed secrets.
